# ADR-001: Keep Request Status as an Event History, Plus a Current-Status Field
*Internal Operations Service Hub*

## 1 Problem

product-spec.md's first functional requirement is: "Employees can submit a service request and view its current status." product-spec.md's acceptance criteria (section 8) don't yet cover this requirement directly — the two examples given are about denied access and search results, not status — but the requirement text itself commits to a "current status," and that commitment isn't credible unless the status can be explained, not just displayed.

Asking the durability question from class - "what must still be true about this request tomorrow, even after everyone has closed their browser" - a single status column cannot answer:
- when did it change,
- who changed it,
- what was it before.

A field is not enough here. The rule that makes the data trustworthy is the ability to explain a status change, not just display one.

## 2 Options

1. **Overwrite current status only.** One `current_status` field on ServiceRequest, overwritten every time the status changes. Simple and cheap to read, but history is destroyed the moment it changes - no way to answer "when did this move to In Progress" or "who rejected it."
2. **Events only, no current-status field.** Every status change is stored as its own row; "current status" is computed by finding the latest event each time it's needed. Full history preserved, but the most common read in the product (show me my request's status) now costs a query over history every single time.
3. **Both, kept in sync (chosen).** RequestStatusEvent stays the append-only source of truth. ServiceRequest keeps a `current_status` field that is updated whenever a new event is appended.

## 3 Decision

Keep both: an append-only RequestStatusEvent history, and a denormalized `current_status` field on ServiceRequest that always reflects the latest event.

## 4 Consequence

- More data and slightly more write work: every status change now writes two things (a new event, and the updated field) instead of one.
- In exchange, the product gets an explainable, auditable history without paying a join or aggregation cost on the most common read (just showing current status).
- This makes the "view its current status" requirement (product-spec.md section 3) actually credible, even though product-spec.md doesn't yet have an acceptance criterion written for it — see the gap noted in section 1 above. It also answers the durability question: even a request that was resolved last week must still have a reconstructable trail of what happened to it and who did it.
